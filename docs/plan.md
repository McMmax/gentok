### Heatmap / virality detection (the trickiest ingestion sub-problem)
- **yt-dlp natively exposes heatmap data.** The `heatmap` field is a documented info-dict field; extraction was fixed by yt-dlp commit **03e85ea**, titled "[ie/youtube] Fix `heatmap` extraction (#8299) â€” Closes #8189, Authored by: bashonly" (merged Oct 7 2023). Running `yt-dlp -J <url>` returns a `heatmap` list of `{start_time, end_time, value}` entries (value = normalized 0-1 replay intensity). This is the recommended primary path â€” zero extra dependencies. (Confirm the exact live JSON keys with a real `yt-dlp -J` run before coding, since older 2022 issue snippets show a different `[[x,y],â€¦]` proposal format that did NOT ship.)
- **YouTube Operational API (Benjamin Loison)** â€” `github.com/Benjamin-Loison/YouTube-operational-API`, tagline "YouTube operational API works when YouTube Data API v3 fails." Exposes `videos?part=mostReplayed&id=...`; per the project's test code the returned JSON gives `mostReplayed.markers[].intensityScoreNormalized` (per Apify's docs, "each point in time of the video has a score between 0 and 1"). Hosted instance at `yt.lemnoslife.com`, but the shared public instance is frequently rate-limited (returns HTTP 400 "unusual traffic"); the maintainer recommends self-hosting. Good as a cross-check/fallback but less robust than yt-dlp's native field. The project itself states plainly (issue #11): "there isn't any official YouTube API endpoint providing the most replayed data."
- **The official YouTube Data API v3 does NOT expose Most Replayed** â€” confirmed. All access is via scraping `ytInitialPlayerResponse`/InnerTube. A video reportedly needs roughly **50,000 views** to have a heatmap (community estimate per Apify's scraper docs: "The video must have at least 50K views to contain a heatmap graph. Not all videos have heatmap graphs" â€” not officially documented by YouTube).
- **Other heatmap tools (fragile fallbacks):** `Dorian25/ytb-most-replayed` (Python, parses the `svg.ytp-heat-map-svg` BÃ©zier path) and npm `youtube-heatmap` (v1.0.3, Puppeteer-based, ~3 years stale). Apify has a paid "YouTube Most Replayed Scraper" actor (~$5/mo) as a managed fallback.
- **Fallback virality detection when no heatmap:** (a) transcript â†’ LLM highlight/virality scoring, the approach used by AI-Youtube-Shorts-Generator, ClipsAI, and FunClip; (b) audio-energy peak analysis; (c) for gaming/VODs, Twitch-chat-spike detection â€” see `Dietech/TwitchHack` (parses chat + audio peaks, 10-sec-window "highlight score" combining volume peaks and keyword spikes like "pog"/"gg"), the classic "PogChampNet" writeup (chat keyword explosions â†’ 30-sec clips + a CNN trained on labeled Overwatch footage), and CV-based `bendawg2010/Auto-clipper` (kill-feed pixel/HSV detection, optional YOLO, and Whisper voice-trigger "clip it").

### Reframing / vertical layouts (16:9 â†’ 9:16)
- **ClipsAI** (`ClipsAI/clipsai`, MIT) â€” transcript-based clip-finding (TextTiling + embeddings) plus a `resize()` that reframes to 9:16 by tracking the active speaker via Pyannote diarization. - **MediaPipe AutoFlip** â€” Google's saliency-aware auto-crop; **officially deprecated.** Google's docs state verbatim: "We have ended support for this MediaPipe Legacy Solution as of March 1, 2023," and "Note: AutoFlip currently only works with OpenCV 3." Do not build on it directly. Use the maintained Python reimplementations instead:
  - **pyautoflip** (`AhmedHisham1/pyautoflip`, MIT) â€” saliency-aware cropping (InsightFace + MediaPipe object detection), scene detection, temporal smoothing, blur/solid-color padding. Simple `reframe_video(input, output, target_aspect_ratio="9:16")` API.
  - **KazKozDev/auto-vertical-reframe** ("verthor", MIT) â€” scene-aware pipeline: PySceneDetect â†’ YOLOv11-seg + ByteTrack â†’ MediaPipe face/pose + saliency â†’ subject ranking â†’ smoothed camera path â†’ 1080Ã—1920 FFmpeg encode. - **Gaming-specific layouts** (split-screen gameplay+facecam, facecam overlay): no polished OSS library does this turnkey. `bendawg2010/Auto-clipper` has a "one click converts any clip to vertical 9:16 with picker layouts â€” webcam, no-cam, or custom frame" feature and is the best reference; otherwise this is custom FFmpeg `filter_complex` work (crop + vstack + overlay).

- **Caption retention data (community wisdom):** OpusClip's analysis of 13.5M clips (Janâ€“Mar 2026) found **80.2% of viral-tier clips use burned-in captions and 78.6% animate them.** Recommended style: sans-serif, bold, â‰¥32pt, high contrast (white + thick black outline), positioned above the TikTok action bar, word-pop for fast delivery / phrase-reveal for slow. ### Reference-TikTok analysis (your differentiator â€” thinnest OSS coverage)
- **Download TikToks + metadata:** yt-dlp supports TikTok. For richer metadata: `davidteather/TikTok-Api` (Python, Playwright-based, needs `ms_token` cookie â€” the most credible maintained option as of 2026); `dfreelon/pyktok` (simple metadata+video CSV export, used by researchers); `Q-Bukold/TikTok-Content-Scraper` (90+ metadata fields incl. hashtags/mentions/music, SQLite progress tracking, no API key). - **Hashtag/trend research:** TikTok Creative Center trending data is available via paid Apify actors (`clockworks/tiktok-hashtag-scraper`, ~$5/1000 results, ~400â€“800 results/hashtag hard cap) and via `TikTok-Api`'s hashtag module (`Hashtag.videos()`). No robust free OSS for Creative Center trending exists â€” expect custom scraping or a paid actor.
- **Font identification from frames:** no strong turnkey OSS. `robinreni96/Font_Recognition-DeepFont` (Keras implementation of Adobe's DeepFont) is the main OSS option; `ChrisBarsolai/Font-Finder` (OCR + CNN) is early-stage; commercial WhatTheFont/Fontspring Matcherator/WhatFontIs are more accurate. Realistically, use an OCR pass (Tesseract/PaddleOCR) + a multimodal LLM (Claude/Gemini vision) to *name* the font, then map to the nearest bundled Google Font.
- **Caption-style / layout analysis of reference clips:** no OSS does this. This is custom work â€” sample frames, run a vision LLM to describe caption position/animation/color/font and layout, and emit a style config your renderer consumes.

### Rendering pipeline
- **FFmpeg** is the universal backbone (H.264/H.265, 1080Ã—1920, `-c:v h264_nvenc` for hardware accel; use `yuv420p` + `+faststart` flags â€” a Windows-corruption fix noted by several faceless-shorts repos).

## Recommendations (staged build plan)

**Stage 1 â€” Core clipping MVP (fork, don't build).** Fork **SamurAIGPT/AI-Youtube-Shorts-Generator** in `--mode local`. You immediately get yt-dlp ingestion + faster-whisper + LLM highlight ranking + vertical crop. Swap its LLM call to Claude (Anthropic) as primary. Add yt-dlp's native `heatmap` field as an additional highlight signal that biases the LLM's segment selection. **Benchmark to advance:** produces a watchable 9:16 clip with correct speaker framing from a YouTube URL end-to-end.

**Stage 2 â€” Captions + layouts.** Vendor **remotion-dev/template-tiktok** for animated word-by-word captions (fits your Next.js frontend; Remotion renders from React). For reframing, wire in **pyautoflip** (general) and keep **auto-vertical-reframe**'s `sports` preset for gaming/action tracking. Build the split-screen/facecam-overlay layouts as parameterized FFmpeg `filter_complex` templates (no good OSS shortcut). **Benchmark:** user can pick a layout (center-crop / split / blur-pillarbox / facecam-overlay) and get animated captions matching OpusClip's high-retention spec (bold sans-serif, â‰¥32pt, white+black-outline, above action bar).

**Stage 3 â€” Reference-based project setup (your moat; mostly custom).** Build the "analyze reference TikToks" layer: download refs via yt-dlp/TikTok-Api â†’ sample frames â†’ run Claude/Gemini vision to extract caption position/animation/color, font (map to nearest bundled Google Font via DeepFont or vision-LLM), and layout â†’ emit a reusable style JSON your renderer consumes. Analyze reference hashtags/descriptions with Claude to generate optimal combinations (remember: fewer hashtags perform better per quso.ai's data). **Benchmark:** a new clip visually matches a supplied reference clip's caption + layout style without manual styling.

**Stage 4 â€” GUI + orchestration polish.** Build the Next.js drop-a-link GUI with an in-browser timeline for manual trimming (reference FunClip's transcript-select UX and openshorts' architecture). Add prompt-based editing control ("make captions bigger", "use the split-screen layout") routed through Claude. Add NVENC hardware-accelerated final render.

**Thresholds that change the plan:**
- If target content is **gaming**, deprioritize ClipsAI/speaker-diarization reframing (built for talking heads) and lead with auto-vertical-reframe + CV/kill-feed detection (Auto-clipper, TwitchHack).
- If the heatmap `value` field is empty for most target videos (sub-50k-view sources), skip heatmap entirely and rely on transcript-LLM scoring.
- If TikTok scraping proves too brittle (cookie/CAPTCHA churn), fall back to a paid Apify actor for reference ingestion rather than maintaining a scraper.

## Caveats
- **Legal/ToS:** YouTube's ToS and TikTok's ToS both restrict automated downloading/scraping; TikTok explicitly prohibits automated scraping (public data is a legal gray area varying by jurisdiction). Reusing others' YouTube content for clipping raises copyright/fair-use questions that intensify with monetization. This is not legal advice â€” treat the tool as personal/research use and review platform terms before any redistribution or monetization.
- **Maintenance risk:** ClipsAI is flagged "maintenance inactive" (Snyk: no PyPI release in 12+ months, "could be considered discontinued"); MediaPipe AutoFlip is officially deprecated (support ended March 1 2023, OpenCV-3-only); `drawrowfly/tiktok-scraper` is dead; the operational-API public instance is rate-limited. Verify current status and prefer the maintained reimplementations noted above before committing.
- **Heatmap availability is not guaranteed** â€” only higher-view videos (~50k+) have it, and YouTube can change the underlying `ytInitialPlayerResponse` structure at any time, breaking scrapers. yt-dlp's native field is the most robust because it's actively maintained, but always keep the transcript-LLM fallback.
- **"One-shot" is optimistic.** Every full-pipeline repo reviewed (MoneyPrinterTurbo, ShortGPT) has documented setup friction (FFmpeg paths, CUDA/cuDNN, moviepy 2.0 breakage, Python version pins, edge-tts API renames). Expect Claude Code to scaffold ~70-80% and require iterative debugging of the media toolchain, especially GPU acceleration and Remotion/Chromium rendering.
- **No single OSS project does reference-style cloning or gaming split-screen layouts** â€” these two areas require the most custom code and are where your build will differ most from any existing repo.
- Star counts and some maintenance dates are point-in-time (mid-2026); confirm the exact live `yt-dlp -J` heatmap JSON keys and current repo stars with a real check before coding against them.
